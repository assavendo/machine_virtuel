# Traçabilité exhaustive du cahier des charges PhoenixVM

**Référence examinée :** \`Cahier_des_charges_VM_Android_Complete_UltraPerformance.txt\`  
**Version source :** 1.0 — 23 novembre 2026  
**Dépôt audité :** \`assavendo/machine_virtuel\`, branche \`main\`  
**Date de l'audit logiciel :** 26 novembre 2026

Ce document suit la numérotation originale du cahier, y compris son numéro 32 utilisé deux fois et l'absence du numéro 31. Il ne renumérote pas la source.

## Légende

- **CODE** : mécanisme logiciel présent dans le dépôt ; cela ne prétend pas qu'un guest complet a déjà été démarré sur un téléphone.
- **PARTIEL** : socle ou API présent, mais fonction non complète, runtime absent, intégration non achevée ou validation manquante.
- **APPAREIL** : validation exigeant un téléphone/SoC réel, un OS invité réel, des autorisations OEM ou une mesure physique ; le code peut préparer le test mais ne peut pas le certifier depuis GitHub.
- **À FAIRE** : exigence logicielle non implémentée ou insuffisamment démontrée.

| 6. Gestion des machines virtuelles | PARTIEL | Modèle persistant et opérations create/clone/start/stop/pause/resume/reboot/delete/import/export/snapshot/restore disponibles. Les commandes de cycle de vie sont maintenant FIFO par VM, les sorties asynchrones vérifient l'identité du processus avant de modifier l'état, et un arrêt ne publie OFF qu'après confirmation de fin du processus avec escalade bornée. Les tests JVM couvrent l'ordre, l'indépendance inter-VM et les scénarios d'escalade ; les arrêts non gracieux passent en RECOVERY, un délai d'arrêt dépassé conserve cette obligation de récupération jusqu'à la sortie effective du processus, les sorties déjà survenues sont classées comme inattendues, la classification des codes de sortie dispose de tests unitaires purs, les démarrages depuis un état persistant orphelin sont bloqués au profit de RECOVERY, admission/registration/fermeture du service sont linéarisées, l'arrêt du service déplace la terminaison bornée en arrière-plan sans supprimer les handles encore vivants, l'échec de readiness d'un backend bloque le fallback si le processus ne meurt pas, les callbacks tardifs conservent RECOVERY, et les écritures d'état runtime entre VM sont sérialisées. Le stockage partagé utilise maintenant des transactions atomiques à l'échelle du processus pour les ajouts, retraits, mises à jour et finalisations de sortie ; les mises à jour d'une VM ne peuvent donc plus être écrasées par l'insertion concurrente d'une autre. La suppression destructive exige désormais OFF confirmé, car ERROR peut encore correspondre à un processus vivant. La stabilité multi-VM/cycles longs reste à valider sur appareil. |
| 7. Création d'une VM | PARTIEL | L'interface Android est maintenant un assistant interactif de sept pages A–G avec progression, Précédent/Suivant et bouton Créer sur la dernière page ; les valeurs restent disponibles entre pages, le sélecteur de fichiers restaure la page active après sélection/annulation/échec, et la validation renvoie à la page propriétaire via une politique pure testée. A — architecture ARM64/x86_64/x86_32 ; B — Linux/Windows/Android/BSD/DOS/ISO personnalisée/disque existant, médias et ADB Android ; C — RAM/vCPU/capacité/format disque ; D — GPU AUTO/logiciel/VirGL/Gfxstream sans promesse d'accélération non prouvée ; E — réseau désactivé/NAT/TAP et redirections uniquement NAT ; F — dossier privé et import multi-fichiers ; G — modes/profils d'optimisation et sécurité. Les ISO, disques et boot artifacts sont copiés dans le stockage privé via fichier temporaire puis renommage atomique, avec une réserve d'espace de 64 Mio ; l'import multi-fichiers est transactionnel et supprime le lot si une copie échoue. Les formats QCOW2/VHDX/VDI/VMDK reconnus par signature sont comparés au format choisi sans parser l'image non fiable ; la création impose unicité du nom/ID, limites de ressources, validation des médias et admission RAM ; l'admission RAM et la transition OFF→STARTING d'un lancement sont effectuées dans une seule mutation atomique de la collection, sérialisée également avec les créations/imports ; les engagements RAM des VM STOPPING/RECOVERY/ERROR sont conservés jusqu'à leur réconciliation ; create/clone/import publient leurs enregistrements par insertion atomique avec revalidation des noms/ID et de l'admission, sans écraser les états runtime des autres VM ; le snapshot froid initial, lorsqu'il est demandé, est terminé avant publication du nouvel enregistrement, afin qu'aucun démarrage ne puisse le concurrencer. Tests unitaires couvrent matrice d'architecture, navigation/routage des validations, redirections, dossiers, signatures de disques et limites de noms. Les extensions x86, les images réellement bootables, les ponts réseau, le GPU et le boot/installation des familles d'OS restent à valider sur appareils réels ; les fichiers VMDK à descripteur externe ne sont pas traités comme disque monolithique. |
| 8. CPU : architecture de performance | PARTIEL | Les chemins ARM64 KVM/TCG et x86 full-system TCG/MTTCG sont configurés ; QEMU conserve la responsabilité de ses Translation Blocks, de leur chaînage et de son JIT TCG natif. La topologie CPU ne retient désormais que les cœurs en ligne et permis par le cpuset du processus ; les classes P/E restent UNKNOWN si les attributs sysfs ne permettent pas une distinction fiable. Au démarrage, le scheduler choisit le nombre effectif de vCPU borné par le nombre demandé, les slots CPU attribuables aux VM actives et la politique thermique ; la demande d'origine de l'utilisateur reste conservée dans la configuration persistée. Après démarrage, l'évolution du scheduler agit sur l'affinité des threads sans hot-unplug/hotplug du nombre de vCPU invité. Si une VM possède davantage de threads vCPU que de slots CPU attribués, tous les TID QMP sont répartis en round-robin sur le masque CPU permis. Si le masque CPU est vide ou non fiable, il ne publie aucune recommandation et conserve le fallback vCPU validé. Il mappe les priorités dans la plage Android/Linux non privilégiée 0–10. Les PID QEMU/crosvm sont résolus par couple exécutable/socket de contrôle par VM afin de ne pas appliquer les mesures ou l'affinité à un lanceur su ; puis il applique via JNI sched_setaffinity l'affinité des threads du backend ; les TID vCPU reçus par QMP sont épinglés individuellement et les I/O threads identifiés par query-iothreads reçoivent un nice moins prioritaire. Les changements d'affinité et de priorité échoués restent non bloquants et sont comptabilisés dans les logs ; les cœurs imposés restent ceux du cpuset autorisé. Profilage : CPU hôte et RSS du processus backend (null/indisponible jusqu'à identification du PID exact et disponibilité du premier delta, jamais zéro fictif), utilisation des threads vCPU, intervalle wall-clock, I/O block par processus (/proc/<pid>/io), I/O réseau/disque système, iowait système, fréquence CPU et thermique sont collectés lorsqu'exposés. Le profilage guest CPU, I/O-wait, IRQ et softirq est désormais disponible en logiciel via un canal QEMU Guest Agent optionnel : activation limitée aux profils Linux, canal virtio-serial/socket privé, synchronisation délimitée, lecture de guest-get-cpustats et calcul de deltas per-CPU avec le nombre de cœurs inclus dans l'échantillon (la commande QGA exige un agent Linux compatible, guest-get-cpustats étant disponible depuis QEMU 7.1). Si l'agent est absent, ancien, non connecté ou non pris en charge, ou si un compteur CPU optionnel (iowait/irq/softirq/steal) n'est pas fourni par le noyau invité, les métriques complètes restent indisponibles et ne sont jamais remplacées par des zéros. Les données guest GPU wait, stalls guest et temps TCG internes ne sont pas inventées : elles restent inconnues tant qu'un compteur QEMU/guest fiable n'est pas branché. Les compteurs de cache/traduction issus des profils applicatifs ne constituent pas une mesure des blocs TCG réels ; les exigences cache persistant et JIT niveaux 1/2 sont poursuivies dans les points 9 et 10. Construction/runtime x86, granularité GPU/audio des threads, disponibilité OEM et application effective d'affinité restent à valider sur appareil. |
| 9. Cache de traduction | PARTIEL | L0 conserve en mémoire les artefacts portables les plus actifs ; L1 est un index d'artefacts/métadonnées mémoire partagé par l'instance applicative unique ; L2 persiste les artefacts et manifests dans le répertoire privé de chaque VM ; L3 est un magasin global optionnel (désactivé par défaut) partagé entre VM uniquement si le fingerprint SHA-256 du code, le guest build, la version du traducteur, l'architecture hôte, les CPU features et le niveau correspondent. Les artefacts ne peuvent être persistés que si le traducteur passe explicitement le marqueur relocationSafe ; ils possèdent ensuite une enveloppe versionnée, un hash d'intégrité et des longueurs validées ; profils et compteurs restent VM-locaux. L'invalidation VM ne supprime pas L3 ; l'invalidation globale est explicite. Les budgets L0/L1 d'entrées et d'octets sont communs aux métadonnées et aux artefacts de chaque niveau, avec éviction LRU unifiée et tests JVM dédiés. Les budgets L2/L3, la taille maximale des artefacts et le nettoyage LRU sont configurables. Tests JVM couvrent empreintes, incompatibilités, niveaux L0–L3, intégrité, invalidation, profil local et quotas. Le runtime QEMU TCG interroge également la commande QMP unstable x-query-jit et conserve les compteurs réellement exposés : TB actifs, code généré/capacité, flushs, invalidations et sauts directs ; ces métriques observent le cache TCG en mémoire et restent distinctes des hits d'artefacts PhoenixVM. Des recettes de build depuis source vérifiée existent maintenant pour les deux cibles full-system : le builder x86 cible x86_64/i386-softmmu et le nouveau builder Android ARM64 cible aarch64-softmmu, tous deux sur QEMU 11.1.3 avec le même SHA-256 source vérifié ; les versions du toolchain et des dépendances ne sont toutefois pas épinglées, donc les builds ne sont pas encore bit-à-bit reproductibles. **Limite majeure :** aucun traducteur du runtime QEMU n'utilise encore l'API d'artefacts PhoenixVM et les Translation Blocks opaques internes de QEMU TCG ne sont pas sérialisés ou rechargés entre lancements. L'intégration à un hook TCG/QEMU, le cycle import/export/invalidation et le branchement du runtime source-buildé dans l'application restent nécessaires pour satisfaire pleinement la réduction du coût de traduction au démarrage ; la recette ARM64 produit actuellement un paquet source-build non encore consommé par l'application. |

## Réalisations logicielles ajoutées pendant l'audit

- Fiabilisation des API Android thermiques, du processus root et des processus auxiliaires.
- Démarrage full-system fail-closed, séparation des firmwares ARM64 et x86_64, contrôle de disponibilité des composants.
- Réécriture de l'installation du runtime : extraction tar contrôlée, chemins limités au staging, vérification SHA-256 de l'ensemble des fichiers de manifeste, staging et rollback.
- QEMU/QMP : arguments validés, contrôle de disponibilité QMP avant l'état RUNNING, pause/reprise/redémarrage/arrêt propre sur QEMU TCG/KVM, requête balloon contrôlée.
- Disques : tailles RAW correctes, commandes qemu-img avec timeouts et sorties drainées, vérification avant compactage et rollback.
- Snapshots froids : manifestes, hashes disque/NVRAM, protection, rétention et restauration transactionnelle.
- Packages VM : limites ZIP, vérification hash, import/export atomique, snapshots portables, signature Ed25519 automatique en streaming et identité protégée par Android Keystore.
- Hyperviseur crosvm : lancement full-system ARM64 réel avec socket de contrôle, commandes pause/reprise/arrêt et fallback vers QEMU lorsque le chemin matériel échoue.
- Add-ons runtime : installation isolée et transactionnelle de virtiofsd/swtpm avec manifeste SHA-256, dépendances natives séparées et outils de build Android ARM64.
- Android guest : persistence des boot artifacts et ADB NAT optionnel dans la configuration/commande QEMU.
- VM clones : copie des artefacts de boot/Android/TPM gérés par PhoenixVM, sans recopier automatiquement les chemins externes.
- Snapshots : snapshot froid initial optionnel à l'installation, rétention et restauration avec vérification SHA-256/rollback.
- Recovery UI : consultation du plan persistant et restauration manuelle d'un snapshot vérifié, sans suppression automatique des données.
- Supply chain : inventaire SBOM reproductible de 91 fichiers prébuilt et 21 composants/licences déclarés, validé en CI.
- Cache metadata L0/L1/L2/L3, fingerprints, validation/invalidation, statistiques, profils et réglage du vrai \`tb-size\` QEMU.
- Scheduler global branché au lancement, admission RAM multi-VM, compteurs CPU process/système et mesures mémoire/thermique/I/O/réseau.
- RFB : correction du message SetEncodings et limites de mémoire pour les dimensions framebuffer.
- Gestes et contrôles d'affichage.
- Tests unitaires ciblés et pipelines GitHub Actions revus.
- Inventaire de licences tiers et provisionnement vérifié du firmware x86 OVMF dans le script de build.

## Bloqueurs non physiques qui restent à traiter avant une release logicielle honnête

1. Le runtime QEMU x86_64/i386 n'est pas dans le bundle Android pinned. Le script de build, l'OVMF vérifié, l'archive avec manifeste SHA-256 et l'import UI avec rollback sont présents ; il reste à construire le binaire pour l'environnement Android cible et à tester sa compatibilité dynamique/boot.
2. Les mécanismes logiciels de construction/import de virtiofsd et swtpm sont maintenant présents. Il reste à produire les artefacts Android ARM64 vérifiés et à valider leur exécution réelle sur appareil.
3. Le cache L0/L1/L2/L3 conserve des profils et métadonnées, pas les Translation Blocks compilés ; un vrai cache inter-lancement demanderait une modification TCG/QEMU et une politique de sécurité/invalidation spécifique.
4. Le moteur JIT personnalisé à plusieurs niveaux n'est pas implémenté ; seule la traduction QEMU TCG réelle et son profilage applicatif sont utilisés.
5. La signature d'export est maintenant automatique et l'import exige une empreinte explicitement approuvée. La rotation/migration des clés et le provisioning institutionnel des clés de confiance restent à définir.
6. Le SBOM couvre les hashes et composants/licences déclarés, mais pas encore une association fichier→composant/licence exhaustive pour tout le runtime.
7. Le niveau de qualité Android/Kotlin final doit être prouvé par un run GitHub Actions complet sur le dernier commit stable, sans annulation par concurrency.

## Travaux explicitement exclus car physiques ou liés au matériel

- Boot réel de Linux/Windows/Android guest et tests des ISOs.
- Autorisation OEM et exécution réelle de KVM/Gunyah/GenieZone/Halla/AVF.
- Compatibilité GPU/Vulkan/Surface/audio/USB réel.
- Benchmark, chauffe, throttling soutenu, batterie, veille et stabilité multi-VM.
- Matrice Snapdragon/Dimensity/Exynos/Tensor.
- Comparaison réelle avec Limbo/QEMU/crosvm sous charges équivalentes.

Ces exclusions ne sont pas présentées comme des « tâches terminées ». Elles sont identifiées comme validations physiques requises, conformément à la portée demandée.
